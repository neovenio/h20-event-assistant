# #25 Builder edit target and assistant plans

## What changed

- `App.startBooking` remembers the edit target; the booking form's `dismissed` now calls `dismissBooking()`, which reopens the builder with the same config and proposal id (null stays null).
- New `App.applyPlan(config)` (used by both `<app-assistant (build)>` hooks):
  - builder not open: behaves like `openBuilder(config)`.
  - builder open and clean: replaces the config, back to step 1, edit target cleared.
  - builder open and dirty: shows an in-app `app-modal` "Je huidige plan vervangen?". `confirmReplace(true)` replaces; cancel/close changes nothing (config and edit target kept).
- Replacement works by recreating `app-event-builder` (`@for (key of [builderKey]; track key)`), since the builder reads `initial` only on init.
- `EventBuilder.dirty()` compares the current config with a JSON baseline taken at init.

## Decision

Chosen behaviour: replace, with confirmation only when there are unsaved edits (as the ticket suggested). An applied plan always clears the edit target so it saves as a new concept.

## Booking round-trip

`startBooking` keeps the builder's baseline and `dismissBooking` passes it back via the `initialBaseline` input, so edits made before booking still count as unsaved. Applying an assistant plan while the booking form is open clears the booking state (config, proposal id, baseline) so a later dismiss cannot restore the old config over the plan.
